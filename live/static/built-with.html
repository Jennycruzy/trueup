Three tools, each doing real work: neatlogs records every run and carries the warning, Entire keeps the record of how every fix was made, and cfo.ai turns the measured costs into a business plan.

neatlogs

The record Witness checks, and the place it warns you.

Every run is recorded

Every Trueup run (planning tests, checking results, writing fixes) and every live demo run is recorded in neatlogs. Each demo run is read straight back from neatlogs, so the page shows exactly what neatlogs stored.

The warning lives inside the record

Witness writes its red TRACE DISAGREE step into the same neatlogs record, under the step that is wrong. A neatlogs detection, "TRACE DISAGREE light", counts every one.

The model key powered Trueup

neatlogs gave every team a model key. It powered the part of Trueup that plans tests, the part that writes fixes, and every call in the live demo. All 44 real calls behind the live result cost $0.0124.

neatlogs caught problems in Trueup's own agent

Trueup set up its own detections in neatlogs to watch itself. Here is what they caught, and what changed.

The AI replied in prose, not data

Incident

The part that writes fixes expects a structured reply. Many replies opened with a sentence like "Let me look more carefully at the exact import text..." instead.

What neatlogs showed

The "model reply was not JSON" detection fired 26 times on 11 Oct. The records showed 14 of 40 fix-writing calls were retried, each resending a prompt of about 25,000 tokens.

How we fixed it

Trueup now reads the first data object in the reply, and then asks the AI for structured replies directly. The detection fell to 5 on 12 Oct, and later test-planning and fix-writing runs needed no retry.

Trueup raised false alarms of its own

Incident

Trueup's checks flagged problems that were not real. 27 came from Trueup itself: it looked for one detail of the record in only one place.

What neatlogs showed

The record held the detail in a second place. Later, the "own false alarm" detection fired 2 times on 11 Oct, when Trueup's checks set aside two problems already fixed on the library's main branch.

How we fixed it

Trueup now reads both places: the suspected problems fell from 58 to 31. Problems set aside are kept on file with the rule that removed them, and never reported as findings.

Fix attempts failed, and were retried

Incident

Some drafted fixes did not apply, or failed the proof step: the new test still failed, or another test broke.

What neatlogs showed

The "fix attempt failed (retried)" detection counted 13 failed tries: 6 on 11 Oct and 7 on 12 Oct. Each record shows the failing test sent back to the AI.

How we fixed it

Failed tries are kept and shown next to each fix. After one failed run overwrote a proven fix's files, Trueup was changed so a failed run can never replace a proven fix.

A fourth detection, "command could not run (exit 2)", watches for Trueup commands that cannot start. It had no hits in the period we pulled.

Entire's code graph finds the code to fix

Before Trueup writes a fix, it asks Entire's code graph where the faulty tracing code lives: a search, then who calls it, then what a change would affect. Plain text search with code parsing always runs next to it, so a search that lands in the wrong place cannot hide the right code.

The honest result. We re-ran the search on the shipped fixes. The graph found 3 of the 12 functions the fixes changed, and on the Arize fix ranked one of them second. Text search found every one of them, or its class. So the graph helps, and the fallback still does most of the work.
